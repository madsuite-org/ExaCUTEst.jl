# ExaCUTEst.jl developer guide

ExaCUTEst provides the CUTEst test set as ExaModels. It locates SIF problem
files, decodes them with ExaModelsSIF, and presents the result through an API
that follows CUTEst.jl. Problems whose SIF files append external Fortran have
native Julia implementations in `src/native/`. Nothing at run time calls
Fortran; CUTEst.jl is a test dependency, used as the reference.

## Layout

```
src/
  ExaCUTEst.jl        module, the list of external-Fortran problems, exports
  collection.jl       set_mastsif, mastsif, list_sif_problems, sif_problem_path
  classification.jl   select_sif_problems and the classf.json table
  classf.json         generated by scripts/build_classification.jl; do not edit
  model.jl            ExaCUTEstModel, -param parsing, sif_variable_names,
                      sif_constraint_names, row_linearity
  native.jl           NATIVE_MODELS registry and element-type routing
  native/             one file per external-Fortran family; *_gpu.jl files
                      hold the KernelAbstractions builders
scripts/
  build_classification.jl    regenerates src/classf.json
  compare_classification.jl  compares it field by field with CUTEst.jl's
test/
  runtests.jl         API contract and agreement with CUTEst.jl on a sample
  native_verify.jl    every native model against the Fortran
  *_gpu_verify.jl     each family's kernels on a device against the CPU
  ba_verify.jl        the BA-L* host builder against the Fortran
  solvesweep.jl       MadNLP over the collection (needs MadNLP; see its header)
  collection/         collection-wide verification; see its README
  gpu/                environment for the verification scripts
```

SIF semantics belong in ExaModelsSIF. A decoder fix goes there; this package
owns the CUTEst-facing API, problem selection, and the native ports.

## Native ports

`src/native/` holds a model only for a problem the decoder refuses, that is,
one whose SIF appends external Fortran (`external_fortran_problems()`, 34
problems). Each has an entry in `NATIVE_MODELS`, so `native_problems()` equals
that list. A decodable problem never goes here. An external-Fortran problem
called with `$-PARAMETER` overrides, or an external-Fortran SIF file outside
the collection, raises `ExaModelsSIF.ExternalFortranError`.

The shape of a port follows what the Fortran depends on:

- Fortran that reads only element parameters is evaluated in Julia at build
  time and constant-folded into an ordinary model (`HS68`/`HS69`, the
  `VANDANIUM*` pair).
- Fortran that depends on the variables becomes a generic Julia function
  behind an ExaModels oracle, with derivatives from automatic differentiation.

Never write such a port as an ExaModels symbolic expression. ExaModels nests a
type parameter per operation, and a chain of about 30 operations does not
finish compiling. Never port the Fortran's hand-coded `G` and `H` arrays:
derivatives come from AD over the one function.

Validate a port through `ExaCUTEstModel`, not through its own constructor
(`test/native_verify.jl` does this). A port can be correct and still be
reached by the wrong name, with the wrong default, or not at all.

Keywords such as `element_hessian`, `ref_param_rounding`, `single` and
`fortran_literals` select between readings of the Fortran, so they are part of
a model's identity. `ExaCUTEstModel` forwards keywords to the native builder,
and a keyword the builder does not take raises a `MethodError`.

### Element-type gate

Whether a port needs a gate on its element type depends on one thing: whether
any of its kernels uses `KernelAbstractions.@atomic`. `@atomic` has no
implementation for a non-bits type, so such a kernel fails at
`T = BigFloat` even with `backend = nothing` (the kernels run through
KernelAbstractions' CPU backend either way). Ports that scatter into shared
slots with atomics route non-bits types to a host-loop builder on
`isbitstype(T)`; see `_ba_model` and `_jimack_model`. Ports where every item is
written by one thread, or that reduce in two stages, need no gate. `BigFloat`
is how a `Float64` result is arbitrated, so the host path is required.

`ba_oracle_model` and `ba_residual` are the BA-L* host builder and its
residual, a native Julia port that uses ExaModels' oracle interface.

## Behaviour that differs from CUTEst.jl

- **Ordering.** CUTEst reorders variables (nonlinear first) and constraints
  (equality and linear first). A model here keeps SIF declaration order.
  Compare against CUTEst.jl by permuting on SIF names
  (`sif_variable_names`, `sif_constraint_names`); a positional comparison
  looks like a decoder bug and is not one.
- **Row linearity.** `nlp.meta.nlin` is 0 for every model, because ExaModels
  does not classify rows. `row_linearity(name)` reads it from the decode, and
  the classification builder uses that.
- **Name clash.** ExaCUTEst exports the same names as CUTEst.jl
  (`list_sif_problems`, `select_sif_problems`, `set_mastsif`,
  `generator_sif_problems`). With both loaded, Julia binds neither, and the
  error reads `UndefVarError: list_sif_problems not defined`. Code that loads
  both qualifies the names; `test/runtests.jl` imports explicitly.

## Problem collections

The collections are lazy artifacts declared in `Artifacts.toml`, the same ones
CUTEst.jl v1.4.0 declares. Each artifact wraps its files in a release-named
directory that changes between releases, so `_sif_dir` discovers the directory
and errors on ambiguity; never hardcode its name. `mastsif()` errors on a set
but invalid `MASTSIF` rather than falling back to the default collection.

## The CUTEst build directory

CUTEst.jl decodes and compiles every problem into one shared directory, so
concurrent `CUTEstModel` builds on one machine corrupt each other and report
`Unable to compile a shared library for the problem`. Every script that builds
a `CUTEstModel` holds a pidlock while doing so:

```julia
using FileWatching.Pidfile: mkpidlock
ref = mkpidlock(() -> CUTEstModel(name), "/tmp/cutest-decode.pid"; wait = true)
```

A `CUTEstModel` must also be finalized before another with the same name is
built. A model built here keeps no global state, and `finalize(nlp)` is
accepted and unnecessary.

## Running the tests

```
julia --project=. -e 'using Pkg; Pkg.test()'
```

Needs `gfortran`, since the agreement tests build `CUTEstModel`s. The decoder's
own validation over the collection lives in ExaModelsSIF.

The verification scripts switch themselves to the `test/gpu` environment
(`test/gpu/activate.jl`), which adds CUDA and CUTEst.jl:

```
julia --project=. test/native_verify.jl            # all of native_problems()
julia --project=. test/native_verify.jl CAR2 SARO  # a subset
julia --project=. test/jimack_gpu_verify.jl        # and ba, hs, colloc, raybends, logit, saro
```

Results append to TSV files under `runs/`, which is not tracked.

`native_verify.jl` compares each native model with the Fortran through
`ExaCUTEstModel`. Where the reference cannot adjudicate a derivative, its
tolerance table records why and compares against a central difference of the
lowest trustworthy derivative instead. Five problems (BLEACHNG, CAR2, ORBIT2,
SARO, SAROMM) supply first derivatives only, and HS67, HS85 and BLEACHNG have
analytic first derivatives that contradict their own values. Tolerances are
not loosened to cover a disagreement.

Each `*_gpu_verify.jl` runs three comparisons: the device against the same
kernels on KernelAbstractions' `CPU()` backend, the host kernels against the
Fortran-verified host port, and the assembled `hess_coord` against `hprod`.
Set `<FAMILY>_GPU_BACKEND=cpu` to run the host comparisons on a machine without
a GPU; the device rows then read 0.0.

`test/collection/` verifies the whole collection on CPU and GPU in two
precisions; its README describes how to run it and how each verdict is
decided.

No GPU test is part of `Pkg.test()`.

### The `test/gpu` environment

CUDA is not a dependency of this package. `test/gpu` is a workspace member of
the package environment (`[workspace]` in `Project.toml`), so the two share one
Manifest and resolve every common package to one version. A CUDA installed in
another environment is not resolved against this one.
`test/gpu/LocalPreferences.toml` pins `CUDA_Runtime_jll` and
`CUDA_Compiler_jll` to 12.9, because later runtimes do not support compute
capability 7.0 (for example the V100 and Quadro GV100).

## Dependencies and local development

`Project.toml` takes ExaModels from the `sif-integration` branch of
madsuite-org/ExaModels.jl and ExaModelsSIF from the `master` branch of
madsuite-org/ExaModelsSIF.jl, through `[sources]`. To work on both packages at
once, develop the sibling checkout into this environment:

```julia
using Pkg
Pkg.develop(path = "../ExaModelsSIF.jl")
```

Pkg then rewrites the `ExaModelsSIF` entry of `[sources]` in `Project.toml` to
that path. Keep that edit out of commits: CI and users resolve the git URL,
and a relative path does not exist on their machines. Native ports with an oracle objective need
ExaModels `sif-integration` at `555b4ed9` or later, which provides `hess!` on
`ScalarNonlinearOracle`, element-typed oracle buffers, and scalar oracles in
the KernelAbstractions backend.

## Regenerating the classification table

```
julia --project=. scripts/build_classification.jl
```

Classification letters come from `CLASSF.DB` in the collection artifact. Sizes
and bound and row-type counts come from decoding each problem, because
`CLASSF.DB` records `V` wherever a size is a `$-PARAMETER`; external-Fortran
problems take them from a `CUTEstModel`. The script refuses to write a partial
table, and cross-checks decode-derived metadata against built models on a
sample. `scripts/compare_classification.jl` compares the result with
CUTEst.jl's `classf.json` field by field.
